# بانک اولیه و عملیات محتوا

## دو لایهٔ داده

بذر: ایدهٔ خامِ دارای شناسه و قصد روشن؛ ۴۵۰ مورد در شش فایل `content/seeds-*.md`. تجربهٔ منتشرشدنی: activity revision با تمام فیلدهای05، قدم‌های اجرایی و تأیید. عدد۴۵۰ به بذرها اشاره می‌کند؛ به‌معنای۴۵۰ خروجی تأییدشده یا۴۵۰ تجربهٔ کاملاً متفاوت برای هر فرد نیست.

هر بذر فقط یک primary دارد، ولی یک تجربه می‌تواند چند نیاز را پوشش دهد. استقلال ابعاد و ادعای طبقه‌بندی روان‌سنجی مطرح نیست. تفاوت یک بذر باید در قصد یا تعامل/مهارت باشد؛ تعویض اسم میوه یا رنگ برای رسیدن به تعداد ممنوع. تشخیص تکرار معنایی در review لازم است؛ تفاوت دقیق بذرهای نزدیک در raw_intent مستند شود.

## ورود و تبدیل

۱. parser جدول Markdown را به `{seed_key,primary_dimension,raw_title,raw_intent}` تبدیل کند. ردیف header و separator نادیده گرفته شود؛ `|` در متن بذر استفاده نشود. prefixهای D/R/A/M/N/F طبق README محتوا هستند و ابهام حروف تکراری ندارند.
۲. validate دقیقاً۷۵رکورد هر فایل،۴۵۰شناسهٔ یکتا و title/intent غیرخالی؛ import ناشناخته state منتشرشده نپذیرد.
۳. dry-run گزارش create/unchanged/conflict/invalid بدهد. seed_key کلید upsert است؛ import مجدد فعالیت تکراری نمی‌سازد. تغییر raw روی activity منتشرشده صرفاً raw را با audit تغییر می‌دهد و نیازمند draft تازه است؛ نسخهٔ منتشرشده بازنویسی نمی‌شود.
۴. metadata خام مانند زمان و قیمت از این بانک استخراج قطعی نشود. cook draft پیشنهادی می‌سازد؛ انسان بررسی می‌کند.
۵. demo اولیه حداقل۲۴ revision دستی بازبینی‌شده، چهار مورد برای هر بُعد و در مجموع پوشش کوتاه/کم‌انرژی/رایگان/solo/home و نمونه‌های together/outdoor داشته باشد. این تعداد تضمین coverage همهٔ contextها نیست.

فایل ورودی ادمین JSON است؛ Markdown seedها منبع توسعه‌اند. CLI converter باید JSON سازگار تولید کند. import عمومی حداکثر۵۰۰ رکورد،۱MB؛ فایل ZIP، کد، لینک دانلود خارجی و HTML قبول نشوند. preview یک‌ساعت و متعلق به actor؛ commit admin با checksum. برای import نتیجهٔ هر ردیف ثبت شود؛ failure جزئی گزارش و retry فقط ردیف‌های ناموفق. commit دوباره همان preview اثر اضافه ندارد.

## چرخهٔ عمر

```text
raw activity → draft → review → published
                   ↘ rejected → draft اصلاح‌شده → review
published → نسخهٔ تازه draft → review → publish جدید
نسخهٔ پیشین → superseded
withdraw کل activity → inactive + archive همهٔ نسخه‌های قابل نمایش
```

برای بازگرداندن activity withdrawn ابتدا revision تازهٔ بازبینی‌شده publish شود؛ publish روی inactive محتوا را در pointer می‌گذارد ولی خودکار active نمی‌کند؛ سپس reactivate صریح. در create اولیه active=true ولی بدون pointer برای کاربر نامرئی است. revisionهای archived به published برنمی‌گردند.

## checklist انتشار

قدم‌ها با metadata یکسان‌اند؛ مدت شامل setup/travel است؛ وسایل و تماس پنهان نیستند؛ هزینه یا رایگان قابل دفاع یا unknown است؛ برای محدودیت نامعلوم true نزده‌ایم؛ عنوان/متن روان فارسی است؛ وعدهٔ سلامت یا شناسایی حال ندارد؛ کار با اختیار کاربر تفریح محسوب می‌شود؛ بذرِ اختیار به تکلیف سامان‌دهی خانه تبدیل نشده؛ تمام فیلدها valid و preview موبایل خواناست؛ شبیه‌بودن به بانک بررسی شده؛ reviewer و audit ثبت‌اند.

رایگان به‌معنای مالک‌بودن ابزار نیست؛ مثلاً نقاشی بدون خرید فقط به کاربری با paper و pen پیشنهاد می‌شود. بیرون‌رفتن بدون GPS و data هوا تنها برای فعالیت‌های سازگار با شرایط اعلام‌شده؛ «پارک نزدیک» را موجود فرض نکن. فعالیت وابسته به ticket، venue یا مسیر خاص تا تأیید منبع و زمان اعتبار، در حالت budget محدود نمایش نگیرد.

بذرهای مکان‌محور مانند سینما،موزه،گالری،بولینگ و اتاق فرار برای گستردگی بانک آمده‌اند. چون نسخهٔ اول city/location/provider مکان ندارد،نسخه‌ای که eligibility آن به محل مشخص،ساعت بازبودن،رزرو یا بلیت وابسته است **در MVP منتشر نشود،حتی برای budget flexible**. generic‌کردن نام مکان،نیاز واقعی به مکان را حل نمی‌کند. این بذرها draft می‌مانند تا ماژول دادهٔ محلی اضافه شود؛ایجنت نباید قیمت یا وجودشان را حدس بزند. گردش عمومی فقط وقتی مستقل از مکان خاص و با زمان/شرایط روشن قابل اجراست قابل انتشار است. بانک باید هم تجربه‌های۵تا۱۵دقیقه‌ای و هم سرگرمی‌های۳۰تا۱۲۰دقیقه‌ایِ قابل اجرای واقعی داشته باشد،بدون طولانی‌کردن مصنوعی فعالیت کوتاه.

## coverage پیش از عرضه

جدول شمارش منتشرشده‌ها برای ترکیب‌های وقت۱۵/۳۰/۶۰، home/outdoor،solo/together،free،energy low و شرایط دسترس‌پذیری تولید شود. سلول کم‌محتوا به تیم محتوا نشان داده شود، نه اینکه الگوریتم constraints را شل کند. نمونهٔ فضای کمبود: کاربر۵دقیقه solo/free/بدون ابزار باید حالت کمبود قابل احترام داشته باشد.

نسخهٔ prompt، الگوریتم و taxonomy در هر خروجی ثبت شوند. انتشار batch بدون review فردی در نسخهٔ اول مجاز نیست. prompt جدید ابتدا روی حداقل۱۲ بذر ثابت از هر شش بُعد و بذرهای مسئله‌دار اجرا و توسط انسان مقایسه شود؛ فقط زیبایی متن کافی نیست.

### اصلاح پوشش محلی — ۹ نوامبر ۲۰۲۶

پس از گزارش مالک دربارهٔ کمبود و جذابیت، کاتالوگ demo به ۱۱۳ تجربهٔ فعال رسید؛ ۱۰۷ نمونهٔ تازه اضافه و ۱۸ نمونهٔ اولیهٔ کلی و مشابه کنار گذاشته شدند. هیچ بذر خامی خودکار پخته یا منتشر نشده است. وضعیت نمایشی، نداشتن تأیید انسانی و منع انتشار عمومی در metadata حفظ می‌شوند. شرح فایل‌ها در `content/README.md` و شمارش بازتولیدپذیر در [22](22-catalog-coverage.md) است.

گزارش با `eligible` واقعی، بدون وسیله و با هوا/روشنایی نامعلوم، ۶۴۸ ترکیب زمان/همراه/محیط/بودجه را می‌سنجد؛ شرط سکوت، اجرای نشسته و بدون پله نیز جدا بررسی می‌شود. افت پوشش باید با افزودن محتوای اجرایی رفع شود. موضوع‌های مسدود، withdrawal، تجربهٔ فعال و جلوگیری از تکرار همچنان می‌توانند نتیجه را کم کنند. رتبه‌بندی با همان وزن‌ها باقی مانده و سلیقه، هدف و وسایل در UI اختیاری شده‌اند؛ شمارش کامل به‌معنای اثبات جذابیت نیست.

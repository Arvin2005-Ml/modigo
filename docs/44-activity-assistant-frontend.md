# تحویل فرانت: راهنما، گفتگو و تصویر هر تفریح

بک‌اند آماده است؛ این برش فایل‌های فرانت را تغییر نداده است. هدف رابط این است که کاربر بتواند در همان کارت تفریح را تصور کند، با یک قدم کوچک شروع کند و اگر گیر کرد سؤال بپرسد. شروع تجربه، تعویض و مرور باید حتی در زمان تولید یا خطای مدل قابل استفاده بمانند.

## از کجا وصل کنید

| جای رابط | شناسه و رفتار |
| --- | --- |
| کارت نتیجهٔ فردی | `IndividualResultsPage.tsx` ← `SingleSuggestion.tsx` ← `ActivityCard` در `Activity.tsx`. فقط از `slate.items[0].revision_id` کارت قابل نمایش استفاده کنید. وقتی کارت حاضر شد تصویرش را درخواست کنید. |
| جزئیات تفریح | در `Funilo.tsx`، شاخهٔ مسیر `/activities/{revisionId}`. شناسه را از همان revision معتبر بگیرید. راهنمای کاتالوگ فوراً دیده شود و هنگام باز کردن جزئیات درخواست راهنما را شروع کنید. چت همان‌جا باز شود. |
| تجربهٔ فعال | در `Funilo.tsx`، شاخهٔ `/experiences/{experienceId}`، از `experience.revision_id` استفاده کنید. فقط اگر تجربه فعال و قابل‌نمایش است، چت و راهنما را در دسترس بگذارید؛ آسان‌ترین دسترسی نزدیک قدم‌های اجراست. از `content_snapshot` برای محتوای اصلی تجربه استفاده کنید. |

برای نگهداری state، گرفتن وضعیت و انجام POSTها از `apps/web/lib/store/api/apiSlice.ts` و helperهای جاری `apps/web/lib/api.ts` استفاده کنید. کلید state، polling و گفت‌وگو `revision_id` است؛ `slot_id` هنگام تعویض می‌تواند ثابت بماند. شرط آغاز درخواست: `revision_id` معتبر، پاسخ اصلی رسیده و `unavailable` برقرار نیست. هیچ کاری برای کارت خالی، کارت حذف‌شده یا پیش‌بارگذاری کارت‌های دیده‌نشده انجام ندهید. برای تصویر می‌توان کنار طرح فعلی یک قاب ثابت گذاشت و پس از آماده‌شدن عوضش کرد.

## API

مسیرها زیر `/api/v1/activity-revisions/{revisionId}/assistant` هستند. اگر از helper `api()` استفاده می‌کنید، پیشوند `/api/v1` را دوباره اضافه نکنید. همهٔ مسیرها نشست معتبر با cookie هم‌مبدأ می‌خواهند. برای POST، JSON و `X-CSRF-Token` را مثل سایر درخواست‌ها بفرستید؛ `Origin` را مرورگر می‌فرستد. کلید idempotency برای این مسیرها الزامی نیست.

| درخواست | نتیجه |
| --- | --- |
| `GET /` (بدون اسلش انتهایی در URL کامل) | `200 AssistantState`، خواندن وضعیت، بدون تماس با مدل |
| `POST /assets/image` با `{}` | `202 AssistantState` وقتی تولید رزرو شده یا در جریان است؛ `200` برای تصویر موجود، حالت demo یا دورهٔ مکث پس از شکست |
| `POST /assets/guide` با `{}` | همان رفتار برای راهنمای متنی |
| `GET /image` | `200` باینری PNG/JPEG/WebP وقتی آماده است؛ در حالت غیرفعال یا قبل از آماده‌شدن `404`. از `image.url` در پاسخ استفاده کنید. |
| `POST /chat` | `200 ChatReply`؛ پاسخ کامل JSON، بدون SSE یا استریم |

```ts
type AssistantStatus = 'idle' | 'pending' | 'ready' | 'failed' | 'disabled';

type AssistantState = {
  revision_id: string;
  mode: 'demo' | 'gapgpt';
  guide_status: AssistantStatus;
  guide: {
    source: 'catalog' | 'gapgpt';
    intro: string;
    first_step: string;
    steps: string[];
    tips: string[];
    lighter_version: string;
  };
  guide_retry_after_seconds: number | null;
  image_status: AssistantStatus;
  image: {url: string; alt: string; source: 'gapgpt'} | null;
  image_retry_after_seconds: number | null;
};

type ChatMessage = {role: 'user' | 'assistant'; content: string};
type ChatInput = {messages: ChatMessage[]};
type ChatReply = {revision_id: string; source: 'demo' | 'gapgpt'; reply: string};
```

نمونهٔ واقعی از شکل درخواست و پاسخ چت چندنوبتی؛ مقادیر صرفاً مثال‌اند:

```json
{"messages":[{"role":"user","content":"برای شروع چی لازم دارم؟"},{"role":"assistant","content":"یک برگه و مداد کنار دستت بذار."},{"role":"user","content":"اگه فقط چند دقیقه وقت دارم از کجا شروع کنم؟"}]}
```

```json
{"revision_id":"11111111-2222-4333-8444-555555555555","source":"gapgpt","reply":"روی برگه فقط اولین چیزی رو که به ذهنت می‌رسه بکش؛ همون برای شروع کافیه."}
```

## چرخهٔ تصویر و راهنما

۱. روی کارت جدید، `POST /assets/image` را یک بار برای revision فعال بزنید؛ در جزئیات همین کار را برای `guide` انجام دهید. اگر صفحهٔ جزئیات تنها ورودی کاربر است، همان‌جا تصویر را هم درخواست کنید. POST خودش پاسخ جاری هر دو بخش را می‌دهد؛ برای آغاز لازم نیست حتماً اول GET بزنید.
۲. `pending` یعنی هر ۲ ثانیه **فقط GET وضعیت** بزنید؛ برای دو بخش یک polling کافی است. polling را پس از آماده/ناموفق شدن هر بخش مورد انتظار، خارج‌شدن از صفحه، تغییر revision یا بعد از ۱۲۰ ثانیه متوقف کنید. بعد از توقف زمانی، یک کنترل «بررسی دوباره» با GET کافی است؛ درخواست ساخت بعدی فقط براساس نتیجهٔ GET. پاسخ یا خطای درخواستِ تفریح قبلی نباید روی کارت تازه اثر بگذارد. از abort در صورت پشتیبانی helper یا کنترل شناسهٔ درخواست استفاده کنید. در صفحه‌ای که فقط تصویر می‌خواهد، وضعیت guide را معیار ادامهٔ polling نکنید.
۳. در `ready`، تصویر را با `<img src={image.url} alt={image.alt}>` و cookie فعلی بگذارید. برای Next Image از `unoptimized` استفاده کنید تا درخواست مستقیم مرورگر به API احرازشده برسد. API عکس را از دامنهٔ فانیلو می‌فرستد؛ آن را با helper مخصوص JSON نگیرید. در صورت خطای بارگیری، به طرح پیش‌فرض برگردید. کنار عکس به‌ویژه برای مقصد واقعی بگویید «تصویرسازی با هوش مصنوعی». نگویید عکس واقعی مقصد است. خود متن روی تصویر نباشد.
۴. در راهنما همیشه `guide` قابل نمایش است. `source: catalog` یعنی همان راهنمای تأییدشده؛ در `pending` یا `failed` هم آن را نشان دهید. اگر `source: gapgpt` شد، عنوانی مثل «راهنمای پیشنهادی دستیار»، `first_step` برجسته و `steps` به‌شکل فهرست شماره‌دار باشد. `tips` و نسخهٔ سبک‌تر اختیاری‌اند. متن کوتاه را ساده نمایش دهید، HTML/Markdown اجرا نکنید. هزینه، مدت، وسایل لازم، شرایط، هشدارها و دسترسی را از کارت یا محتوای کاتالوگ بگیرید؛ این فیلدها و دکمهٔ «شروع» تابع متن دستیار نیستند.
۵. `failed` یعنی طرح قبلی/راهنمای کاتالوگ و دکمهٔ اختیاری «دوباره امتحان کن». POST را پیش از `*_retry_after_seconds` تکرار نکنید؛ صفر یعنی می‌توان درخواست ساخت تازه داد. در `demo`، تصویر `disabled` است؛ کنترل تولید را نشان ندهید و پاسخ نمونه را «نمایشی» بنامید. حالت `idle` یعنی هنوز درخواستی برای ساخت ثبت نشده است. پس از مرورِ برگشتی، اگر نسخه هنوز در cache سرور باشد، POST نتیجهٔ موجود را می‌دهد.

## چت

- نزدیک دکمهٔ شروع یا قدم اول، «دربارهٔ این تفریح بپرس» و چند سوال عمل‌محور مثل «قدم اول چیه؟»، «چی لازم دارم؟» و «نسخهٔ ساده‌ترش چیه؟» بگذارید. فرستادن سؤال نمونه با کلیک صریح کاربر انجام شود.
- پیش از اولین ارسال در حالت واقعی این متن یا معادلش را نشان دهید: «پیام‌هایی که می‌فرستی برای پاسخ به گپ‌جی‌پی‌تی ارسال می‌شن. اطلاعات شخصی نفرست.» پیوند [شرایط GapGPT](https://aigap.app/rules) همان‌جا در دسترس باشد. متن چت را در analytics، log سمت فرانت یا localStorage ذخیره نکنید؛ سرور فانیلو هم تاریخچه را نگه نمی‌دارد.
- برای هر ارسال فقط آخرین چهار رفت‌وبرگشت **کامل** و سؤال تازه را بفرستید؛ آرایه ۱ تا ۹ پیام، یکی‌درمیان `user` و `assistant` و همیشه با `user` شروع و تمام شود. متن پیام کاربر ۱ تا ۶۰۰، پاسخ قبلی ۱ تا ۱۶۰۰ و مجموع حداکثر ۶۰۰۰ نویسه پس از trim. در صورت نیاز زوج کامل قدیمی‌تری را حذف کنید. نوع `system` یا اطلاعات حساب نفرستید.
- برای هر گفت‌وگو هم‌زمان فقط یک سؤال بفرستید. موقع ارسال، سؤال و ورودی حفظ شوند؛ پاسخ با همان `revision_id` اضافه شود. شبکه یا خطا باعث افزودن یک جواب ساختگی نشود. در صورت شکست، همان سؤال را با اقدام صریح دوباره بفرستید؛ ارسال خودکار مجدد انجام نشود. روی تعویض کارت، خروج از حساب یا بسته‌شدن تجربه، نشست گفتگو را از UI پاک یا جدا کنید.
- فارسی، RTL، متن قابل انتخاب و شکستن خط‌ها حفظ شود. برچسب ورودی و دکمهٔ ارسال، وضعیت انتظار و پاسخ با `aria-live="polite"` در دسترس باشند؛ اگر پنل گفتگو modal است، focus باز و بسته‌شدن را مدیریت کنید. برچسب `source: demo` را «پاسخ نمایشی» و `source: gapgpt` را «پاسخ دستیار گپ‌جی‌پی‌تی» بنامید.

## خطا و پذیرش

خطاها مثل بقیهٔ API در `error.code` و `error.message` هستند. `401 AUTH_REQUIRED`: ورود دوباره؛ `403 CSRF_FAILED`: helper فعلی فقط یک بار توکن را تازه می‌کند؛ `404 NOT_FOUND` یا `410 CONTENT_WITHDRAWN`: دستیار را برای آن نسخه ببندید و وضعیت منبع اصلی را تازه کنید؛ `422 VALIDATION_ERROR`: ورودی را اصلاح کنید؛ `429 RATE_LIMITED` یا `503 ASSISTANT_BUSY`: اگر header `Retry-After` در لایهٔ API در دسترس است، زمان را رعایت کنید. helper فعلی header را به UI نمی‌رساند؛ برای شمارش دقیق آن را به metadata خطا اضافه کنید. `503 ASSISTANT_UNAVAILABLE` یا خطای شبکه: پیام کوتاه، راهنمای کاتالوگ همچنان قابل استفاده، تلاش مجدد دستی.

برای `ASSISTANT_BUSY` در ساخت تصویر، فقط اگر همان revision هنوز روی صفحه است یک تلاش خودکار بعد از `Retry-After` (پیش‌فرض ۵ ثانیه) مجاز است؛ پس از آن کنترل تلاش مجدد دستی کافی است. برای 429 و چت خودکار تکرار نکنید. اگر از helper فعلی استفاده می‌کنید، POSTهای دستیار را از ثبت کلیدهای موقت idempotency در `pending` معاف کنید تا متن چت پس از شکست شبکه در آن map نماند.

معیار تحویل: تصویر پس از آماده‌شدن در **هر کارت دیده‌شده** نمایش داده شود؛ جابه‌جایی سریع بین کارت‌ها تصویر اشتباه نیاورد؛ درخواست تصویر و راهنما دکمهٔ شروع، قبلی/بعدی و تعویض را معطل نکند؛ چت چندنوبتی فقط دربارهٔ همان revision باشد؛ حالت demo، timeout، قطع شبکه و خطای تصویر با طرح و متن اصلی قابل استفاده بمانند. در موبایل ۳۶۰ پیکسل، RTL، زوم ۲۰۰٪ و صفحه‌کلید بررسی کنید.

## اجرای بک‌اند برای تست

پیش‌فرض `LLM_PROVIDER=demo`، بی‌نیاز از کلید، با Mongo عمومی طبق [سند24](24-mongodb-storage.md). برای تولید واقعی، در محیط سرور `LLM_PROVIDER=gapgpt` و `GAPGPT_API_KEY` را تنظیم و API را راه‌اندازی مجدد کنید. `GAPGPT_ASSISTANT_MODEL=gpt-4.1-mini` و `GAPGPT_IMAGE_MODEL=gemini-2.5-flash-image` پیش‌فرض‌اند. مدل و کلید هیچ‌وقت تنظیم فرانت نیستند.

اگر سرویس تصویر را با URL روی CDN دیگری برگرداند، اپراتور پس از تأیید مالکیت CDN، **فقط نام میزبان دقیق** را در `GAPGPT_IMAGE_HOSTS` زمان اجرای سرور اضافه کند (چند نام با ویرگول). خروجی base64 به میزبان اضافی نیاز ندارد. پس از فعال‌سازی واقعی سه فراخوانی guide، image و chat را با یک پیشنهاد منتشرشده بررسی کنید؛ برای تصویر، GET باینری هم باید ۲۰۰ بدهد.

برای عملیات: حداکثر دو ساخت راهنما، دو ساخت تصویر و چهار پاسخ چت هم‌زمان‌اند. سقف ساخت روزانه برای هر حساب/کل برنامه، تصویر ۲۰/۱۵۰ و راهنما ۳۰/۳۰۰ است؛ پاسخ آمادهٔ cache سهمیه نمی‌گیرد. چت واقعی برای هر حساب ۱۰ درخواست در دقیقه و ۶۰ در روز، و برای کل برنامه ۱۲۰۰ در روز سقف دارد. تصویر تا ۴ MiB، راهنما و تصویر موفق تا ۳۰ روز و تلاش ناموفق با مکث پیش‌فرض ۲ دقیقه نگه داشته می‌شوند. اگر API وسط تولید متوقف شود، تا ۳ دقیقه ممکن است `pending` دیده شود؛ سپس کاربر می‌تواند دوباره تولید را درخواست کند.

# راهنمای پیاده‌سازی فرانت دستیار تفریح

بک‌اند دستیار تفریح وجود دارد؛ فرانت هنوز آن را فراخوانی نمی‌کند. این سند نقشهٔ اجراست. در صفحهٔ نتیجه، کاربر تصویرسازی پیشنهاد فعلی را می‌بیند؛ در جزئیات، می‌تواند راهنمای تکمیلی را بخواند یا دربارهٔ همان تفریح سؤال بپرسد؛ در تجربهٔ فعال، کمک کنار قدم‌های اجرا در دسترس است. اگر دستیار کند، خاموش یا ناموفق باشد، کاربر همچنان می‌تواند پیشنهاد را ببیند، جابه‌جا شود، تجربه را شروع کند و آن را پایان بدهد.

این قابلیت به صفحهٔ مستقل چت، تغییر مسیرهای موجود، مدل دادهٔ تازه، کتابخانهٔ جدید یا تغییر الگوریتم پیشنهاد نیاز ندارد. صفحه‌های فهرست کشف و ذخیره‌ها فقط از مسیر جزئیات به دستیار می‌رسند؛ برای ردیف‌های فهرست، تاریخچه، ادمین، صفحهٔ پایان و بازخورد درخواستی ارسال نشود. مرجع رفتار سرور [مسیرهای HTTP](../apps/api/app/http/routes.py)، [نوع‌ها و اعتبارسنجی](../apps/api/app/modules/activity_assistant/schemas.py) و [سرویس دستیار](../apps/api/app/modules/activity_assistant/service.py) است. این دستیار جدا از [ایجنت تولید محتوای ادمین](08-ai-agent.md) است و خروجی آن بخشی از محتوای منتشرشده یا امتیازدهی نمی‌شود.

## ۱. کاربر هر قابلیت را کجا می‌بیند؟

| صفحه | زمان فعال‌شدن و شناسه | چیزی که کاربر می‌بیند |
| --- | --- | --- |
| نتیجهٔ فردی، `/individual/results?slate=…` | بعد از احراز نشست و نمایش `sessionQuery.currentData.items[0]`، اگر `revision_id` دارد و `unavailable` نیست. درخواست فقط برای کارت فعلی؛ هنگام مرور یا تعویض، با تغییر revision محدودهٔ قبلی بسته شود. | یک قاب ثابت برای تصویر بالای کارت. تا زمان آماده‌شدن یا در صورت خطا، طرح فعلی دیده شود. عنوان، زمان، هزینه، دلیل پیشنهاد، «ببینمش»، ذخیره، مرور و تعویض طبق رفتار فعلی بمانند. چت و متن راهنما روی کارت نتیجه نمایش داده نشوند. |
| جزئیات، `/activities/{revisionId}` | بعد از موفقیت دریافت جزئیات و تطابق `detail.id` با مسیر فعلی؛ در این صفحه راهنما و تصویر لازم‌اند. از ورود مستقیم، کشف، ذخیره‌ها و نتیجهٔ فردی پشتیبانی شود. | تصویر نزدیک عنوان؛ قدم‌های کاتالوگ فوراً قابل خواندن‌اند. بعد از قدم‌ها، بخش جمع‌شدنی «راهنمای تکمیلی» و دکمهٔ «دربارهٔ این تفریح بپرس» قرار بگیرند. دکمهٔ فعلی شروع/ادامه بیرون پنل و مستقل بماند. |
| تجربهٔ فعال، `/experiences/{experienceId}` | پس از تطابق شناسهٔ تجربه با مسیر، `status === "active"`، داشتن `revision_id` و `content_snapshot` و برقرار نبودن `unavailable`. از `experience.revision_id` برای دستیار استفاده شود. | متن اصلی از همان `content_snapshot` و پنل کوچک راهنما/چت نزدیک قدم‌ها. تولید تصویر برای این صفحه آغاز نشود. پایان و لغو همیشه طبق اعتبار تجربه از API عمل کنند؛ اگر محتوا پس گرفته شده، دستیار پنهان شود ولی امکان پایان یا لغو طبق روال فعلی بماند. |

شناسهٔ کلید دستیار `revision_id` است. `slot_id` ممکن است پس از تعویض ثابت بماند و `activity_id` ممکن است چند revision داشته باشد. `experienceId` نیز فقط شناسهٔ خود تجربه است. لینک و پارامترهای برگشت مانند `from`، `slate` و `slot` و اعتبارسنجی شروعِ کاتالوگی یا شروع از پیشنهاد را تغییر ندهید.

برای refresh منبع اصلی بعد از حذف محتوا، از API جاری همان صفحه استفاده کنید: `sessionQuery.refetch()` در نتیجه، `getRevision(detail.id)` در جزئیات و `getActiveExperience()` در تجربهٔ فعال. درخواست refresh باید فقط یک‌بار برای خطای همان محدوده از دستیار آغاز شود. خروجی refresh هم پیش از به‌روزرسانی باید با مسیر و نشست جاری تطبیق داده شود.

## ۳. قرارداد HTTP که فرانت باید رعایت کند

آدرس پایهٔ مرورگر `/api/v1/activity-revisions/{revisionId}/assistant` است. هنگام استفاده از `api()`، مسیر را با `/activity-revisions/…` بدهید؛ helper خودش `/api/v1` را اضافه می‌کند. تمام درخواست‌ها با cookie نشست و هم‌مبدأ هستند. POSTها بدنهٔ JSON و `X-CSRF-Token` معتبر می‌خواهند؛ `Origin` را مرورگر می‌فرستد. دستیار `Idempotency-Key` نمی‌خواهد. draft و نسخهٔ ناموجود در دسترس نیستند؛ نسخهٔ پیشین قابل‌نمایش را با نسخهٔ جدید جایگزین نکنید. تصویر باینری است و از مسیر JSON خوانده نمی‌شود.

| درخواست نسبت به آدرس پایه | پاسخ و کاربرد |
| --- | --- |
| `GET` بدون اسلش انتهایی | `200 AssistantState`. فقط خواندن وضعیت؛ تولید را شروع نمی‌کند. |
| `POST /assets/guide` یا `POST /assets/image` با `{}` | `202 AssistantState` اگر تولید در انتظار است؛ `200 AssistantState` برای حالت آماده، demo یا مکث پس از شکست. ملاک رفتار UI، فیلد وضعیت همان دارایی در بدنه است. هر پاسخ، وضعیت هر دو دارایی را دارد. |
| `GET /image` | وقتی آماده باشد `200` باینری PNG/JPEG/WebP. قبل از آماده‌شدن، در demo یا بعد از انقضا ممکن است `404` بگیرید. آدرس را از `image.url` بگیرید. |
| `POST /chat` | `200 ChatReply`. درخواست و پاسخ کامل JSON هستند؛ استریم و شناسهٔ تاریخچهٔ سمت سرور ندارند. |

```ts
type AssetKind = 'guide' | 'image';
type AssistantMode = 'demo' | 'gapgpt';
type AssetStatus = 'idle' | 'pending' | 'ready' | 'failed' | 'disabled';
type AssistantGuide = {
  source: 'catalog' | 'gapgpt';
  intro: string;
  first_step: string;
  steps: string[];
  tips: string[];
  lighter_version: string;
};
type AssistantState = {
  revision_id: string;
  mode: AssistantMode;
  guide_status: AssetStatus;
  guide: AssistantGuide;
  guide_retry_after_seconds: number | null;
  image_status: AssetStatus;
  image: { url: string; alt: string; source: 'gapgpt' } | null;
  image_retry_after_seconds: number | null;
};
type ChatMessage = { role: 'user' | 'assistant'; content: string };
type ChatInput = { messages: ChatMessage[] };
type ChatReply = { revision_id: string; source: AssistantMode; reply: string };
```

در `demo`، وضعیت راهنما `ready` با `source: "catalog"` و تصویر `disabled` است. `ready` به‌تنهایی به معنی تولید با مدل نیست. مقدار `guide` حتی وقتی تولید راهنما هنوز آغاز نشده یا شکست خورده وجود دارد؛ قبل از دریافت یا در صورت خطای شبکه، خود محتوای صفحه همان مرجع اصلی است.

## ۴. چرخهٔ تصویر و راهنما

1. **محدوده:** کلید نمونهٔ فعال از نشست حساب، revision و محل نمایش تشکیل شود. تغییر هرکدام، خروج از مسیر، پایان/لغو تجربه یا از دست رفتن دسترسی باید تایمر و درخواست UI قبلی را لغو و حالتی تازه ایجاد کند. علاوه بر abort، قبل از پذیرفتن پاسخ یا خطا شناسهٔ اجرای جاری را کنترل کنید؛ برای پاسخ موفق تطابق `revision_id` را هم بررسی کنید. لغو مرورگر ممکن است کار رزروشدهٔ سرور را متوقف نکند. پاسخ دیررس، حتی از revision هم‌نام در نشست قبلی، نباید UI را تغییر دهد.
2. **ورود:** پس از داشتن منبع اصلی معتبر، ابتدا یک GET وضعیت بزنید. این کار جلوی POST بی‌نیاز برای cache آماده، demo و کارت برگشتی را می‌گیرد. برای هر دارایی موردنیاز با وضعیت `idle` یک POST خودکار در هر بار فعال‌شدن محدوده کافی است. در جزئیات، `guide` را پیش از `image` درخواست کنید. درخواست‌ها و تصمیم‌های وضعیت در همان محدوده سری باشند تا یک snapshot قدیمی، وضعیت تازه را عقب نبرد؛ منتظر آماده‌شدن guide برای فرستادن POST تصویر نمانید.
3. **انتظار:** اگر هر دارایی موردنیاز `pending` است، هر ۲ ثانیه پس از پایان درخواست قبلی فقط GET وضعیت بزنید؛ یک زمان‌بند برای هر دو کافی است. از اولین `pending` حداکثر ۱۲۰ ثانیه بررسی کنید و در تب مخفی GET دوره‌ای نزنید. با بازگشت به تب، اگر زمان باقی مانده و درخواست دیگری در جریان نیست یک GET فوری بزنید. وقتی دیگر هیچ دارایی موردنیازی pending نیست، صفحه بسته می‌شود، شبکه خطا می‌دهد یا مهلت تمام می‌شود، زمان‌بند متوقف شود؛ هنگام اتمام مهلت GET در حال انتظار هم لغو شود. `guide_status` نباید polling کارتِ صرفاً تصویری را باز نگه دارد. بعد از مهلت، «بررسی دوباره» یک GET می‌زند؛ اگر هنوز pending است فقط وضعیت را نشان بدهید. عبور از مهلت مرورگر به معنی شکست تولید نیست.
4. **آماده:** تصویر را مستقیم با `img` یا `next/image` با `unoptimized` بارگیری کنید تا cookie به API هم‌مبدأ برسد. فقط URL نسبی همان مسیرِ تصویر برای revision فعلی پذیرفته شود. `image.alt` را استفاده کنید و زیر عکس بنویسید «تصویرسازی با هوش مصنوعی». عکس مقصد واقعی معرفی نشود. قاب با نسبت ثابت پیشنهادی ۱۶:۹ و `object-fit: cover` در موبایل و دسکتاپ جای دکمه‌ها را جابه‌جا نکند. خطای decode/بارگیری همان قاب پیش‌فرض را برگرداند. خطای خود عنصر عکس به‌تنهایی دلیل withdrawn بودن محتوا نیست؛ می‌توان یک GET وضعیت انجام داد. با هر render یا خطای عکس دوباره تولید آغاز نشود.
5. **راهنما:** قدم‌های کاتالوگ همیشه در بدنه بمانند. اگر `guide.source === "gapgpt"`، داخل بخش اختیاری راهنما `intro`، `first_step` برجسته، `steps` شماره‌دار، و در صورت وجود `tips` و نسخهٔ سبک‌تر نمایش داده شوند. اگر `source === "catalog"`، همان قدم‌های کاتالوگ در بدنه کافی‌اند و پنل متن تکراری نسازد. متن دستیار فقط متن ساده است. مدت، هزینه، وسایل، دسترسی، شرط شروع، هشدارها و اطلاعات مقصد از محتوای رسمی نمایش داده شوند.
6. **شکست یا غیرفعال:** `failed` یعنی fallback و راه «دوباره امتحان کن». زمان باقی‌ماندهٔ مکث هر دارایی از `*_retry_after_seconds` می‌آید؛ صفر یعنی تلاش دستی مجاز است. پایان شمارشِ مکث فقط دکمه را فعال کند. تلاش دستی ابتدا GET می‌زند، سپس اگر دارایی هنوز `idle` یا `failed` با مکث صفر است POST می‌زند. برای `disabled` و demo، کنترل تولید/تلاش مجدد نمایش داده نشود. متن وضعیت کوتاه بماند: «تصویر هنوز آماده نشده» یا «فعلاً می‌تونی از قدم‌های همین تفریح استفاده کنی».

## ۵. چت: رفتار، ورودی و حریم خصوصی

- یک پنل بازشوندهٔ درون صفحه کافی است. کنار راهنما دکمهٔ «دربارهٔ این تفریح بپرس» با `aria-expanded` و `aria-controls` بگذارید. پیشنهادهای «قدم اول چیه؟»، «چی لازم دارم؟» و «نسخهٔ ساده‌ترش چیه؟» فقط ورودی را پر کنند؛ درخواست با دکمهٔ «بفرست» یا submit صریح فرم ارسال شود. بازکردن پنل هیچ پیام خودکاری نفرستد.
- پیش از اولین ارسال در حالت `gapgpt`، حتی اگر تصویر/راهنما هنوز آماده نیست، بنویسید «پیام‌هات برای پاسخ به گپ‌جی‌پی‌تی فرستاده می‌شن. اطلاعات شخصی نفرست.» [شرایط GapGPT](https://aigap.app/rules) همان‌جا در دسترس باشد. اگر حالت نامعلوم است، همان‌جا بگویید «در حالت واقعی، پیام‌هات برای پاسخ به گپ‌جی‌پی‌تی فرستاده می‌شن.» در حالت demo، برچسب «پاسخ نمایشی» بدهید. اگر منبع پاسخ با حالت قبلی متفاوت بود، برچسب پاسخ از `ChatReply.source` تعیین شود.
- فقط سؤال جدید و حداکثر چهار زوج **کامل**ِ سؤال/جواب قبلی از همان گفتگو بفرستید. ابتدا متن را با NFC هم‌ارز و trim کنید؛ سؤال ۱ تا ۶۰۰ و هر پاسخ قبلی ۱ تا ۱۶۰۰ کاراکتر. مجموع حداکثر ۶۰۰۰ کاراکتر و آرایه ۱ تا ۹ عضو، با ترتیب `user, assistant, …, user`. شمارش مثل Python بر پایهٔ code point باشد (در JS، مثلاً `Array.from(text).length`). برای رعایت سقف مجموع، اول قدیمی‌ترین زوج کامل را حذف کنید. اگر سؤال فعلی نامعتبر است خطای فارسی کنار ورودی بدهید؛ آن را بی‌صدا نبُرید. پیام ناموفق یا در انتظار، نوبت کامل حساب نشود.
- بدنه فقط `messages` دارد. نمونه: `{"messages":[{"role":"user","content":"چی لازم دارم؟"},{"role":"assistant","content":"یک برگه کنار دستت بذار."},{"role":"user","content":"اگه وقت کم دارم از کجا شروع کنم؟"}]}`. اطلاعات حساب، پاسخ‌های پرسش‌نامه، مکان کاربر و پیام `system` ارسال نشوند.
- در هر گفتگو یک ارسال در لحظه. سؤال ارسال‌شده و payload را تا نتیجه در حافظهٔ همان پنل نگه دارید. موقع انتظار «دارم جواب رو می‌گیرم…» اعلام شود. فقط پاسخ معتبر همان revision را به‌عنوان نوبت کامل ثبت کنید. خطا، جای پاسخ چت را با متن ساختگی پر نکند؛ سؤال برای اصلاح یا تلاش دستی بماند. روی خطای شبکه/timeout، ارسال خودکار دوباره انجام نشود؛ یک درخواست ممکن است پیش از قطع شبکه به سرور رسیده باشد.
- بسته‌شدن و بازکردن همان پنل در همان صفحه می‌تواند گفتگو را نگه دارد؛ تعویض revision، خروج از صفحه، پایان/لغو، تغییر حساب یا انقضای نشست آن را پاک کند. متن یا بدنهٔ درخواست را در storage مرورگر، URL، Redux، لاگ، analytics، Service Worker یا ابزار ثبت خطا ثبت نکنید. فانیلو تاریخچهٔ گفتگو را در سرور ذخیره نمی‌کند؛ این گزاره دربارهٔ سیاست نگهداری provider نیست.
- پیام و راهنمای تولیدی را به‌شکل متن سادهٔ React با شکست خط نمایش دهید؛ HTML، Markdown یا لینک‌سازی خودکار اجرا نشود. برچسب ورودی و خطای مرتبط، فوکوس واضح، اعلان مؤدبانهٔ ارسال و پاسخ، ترتیب Tab طبیعی و حفظ فوکوس هنگام رسیدن پیام لازم است. همهٔ متن‌ها فارسی و RTL باشند. دکمه‌ها در موبایل در دسترس بمانند و با متن بلند یا زوم ۲۰۰٪ اسکرول افقی ایجاد نشود.

## ۶. خطاها و رفتار صفحه

بدنهٔ خطا شامل `error.code`، `error.message`، `error.fields` و `error.request_id` است. تصمیم UI با کد و وضعیت باشد، نه با مقایسهٔ متن خطا. شمارش مکث از مقدار معتبر `Retry-After` پاسخ HTTP یا فیلدهای انتظار در بدنهٔ وضعیت گرفته می‌شود؛ این دو منبع برای یک مفهوم نیستند.

| خطا | واکنش |
| --- | --- |
| `401 AUTH_REQUIRED` | پاک‌سازی دستیار و چت و فراخوانی `expireSession(returnTo)` با مسیر درونی فعلی؛ بعد از ورود مجدد پیام قبلی خودکار ارسال نشود. |
| `403 CSRF_FAILED` | helper فعلی یک بار برای رد صریح CSRF توکن را تازه می‌کند و با همان بدنه تکرار می‌کند. اگر بار دوم هم رد شد پیام فارسی نشان دهید؛ وارد چرخهٔ retry نشوید. سایر 403ها خودکار تکرار نشوند. |
| `404 NOT_FOUND` یا `410 CONTENT_WITHDRAWN` از وضعیت، تولید یا چت | دستیار همان revision را ببندید، متن/تصویر تولیدی را پاک کنید و منبع اصلی صفحه را یک‌بار تازه کنید. اگر API اصلی هنوز محتوا را قابل‌نمایش اعلام کرد، همان محتوا و کارهای مجازش بمانند؛ دستیار برای همان محدوده خودکار دوباره روشن نشود. خطای باینری تصویر مسیر جداگانهٔ بخش ۴ دارد. |
| `422 VALIDATION_ERROR` | در چت ورودی حفظ شود و خطای خوانا کنار آن بیاید. خطای POST دارایی دستی/محلی بماند و خودکار تکرار نشود. |
| `429 RATE_LIMITED` یا `503 ASSISTANT_BUSY` | تلاش دستی با رعایت `Retry-After`؛ بدون POST خودکار. سرور در حالت busy فعلاً ۵ ثانیه برمی‌گرداند. اگر header معتبر نرسید، پیام «کمی بعد دوباره امتحان کن» کافی است و زمان ساختگی به کاربر نشان ندهید. این محدودیت به شروع/پایان/تعویض سرایت نکند. |
| `503 ASSISTANT_UNAVAILABLE`، `TEMPORARILY_UNAVAILABLE`، خطای شبکه یا proxy | متن کوتاه در همان بخش، fallback کاتالوگ/قاب پیش‌فرض، و تلاش دستی. polling پس از خطای GET متوقف شود و با اقدام کاربر از GET آغاز شود. |

## ۷. ترتیب اجرا و معیار پذیرش

۱. **قرارداد و transport:** typeها، مسیرها، معافیت idempotency، لغو و انتقال `Retry-After`. در [تست API فرانت](../apps/web/tests/api.test.cjs) بررسی کنید POST چت بدنهٔ صحیح، cookie و CSRF دارد و پس از شکست شبکه متن در map کلیدها باقی نمی‌ماند. رفتار قبلی retry CSRF و idempotency شروع/تعویض حفظ شود. در [تست store](../apps/web/tests/store.test.cjs) انتقال خطا و header برای endpointهای دارایی بررسی شود.

۲. **تصویر، بعد راهنما:** ابتدا حالت‌های `idle → pending → ready`، `failed` و `demo` را در کارت نتیجه بسازید؛ سپس جزئیات و تجربهٔ فعال را وصل کنید. در [آزمون مرورگر](../apps/web/tests/browser.test.cjs) مسیرهای fake همان API را با revisionهای متمایز پیاده کنید. یک slate با `slot_id` ثابت و تغییر A → B → A بسازید و پاسخ A را عمدی دیر برگردانید؛ تصویر اشتباه یا polling اضافه نباید برسد. کش آماده، خطای باینری، توقفِ مهلت، مکث، 429/503 و نسخهٔ withdrawn را هم بررسی کنید. فهرست، نتیجهٔ خالی/withdrawn، مهمان و مود demo نباید POST تولید بفرستند.

۳. **چت:** تابع ساخت پیام با مرزهای ۶۰۰، ۱۶۰۰ و ۶۰۰۰، NFC و زوج کامل آزموده شود. در مرورگر، کلیک دوباره در زمان انتظار نباید درخواست دوم بفرستد؛ سؤال بعدی پس از دریافت پاسخ باید تاریخچهٔ همان revision را داشته باشد. خطای شبکه جواب مصنوعی و resend خودکار نسازد، و تعویض کارت، logout، انقضای نشست یا پایان تجربه، پاسخ دیررس و پیش‌نویس قبلی را برنگرداند. در mockها فقط متن تست استفاده کنید.

۴. **آزمون مسیر کامل:** ورود ← سؤال‌ها ← پیشنهاد ← جزئیات ← شروع ← پایان ← بازخورد اختیاری را در حالی اجرا کنید که دستیار pending است یا خطا می‌دهد. «پیشنهاد قبلی/بعدی»، تعویض، ذخیره، شروع، لغو و پایان طبق قواعد فعلی کار کنند؛ در حالت برداشت محتوا، تجربهٔ فعال همچنان قابل پایان/لغو باشد. بازبینی صفحه‌کلید، RTL، `aria-live`، زوم ۲۰۰٪ و عرض‌های ۳۶۰، ۳۹۰، ۷۶۸ و ۱۴۴۰ را طبق [سند طراحی](03-design.md) انجام دهید. بررسی کنید درخواست باینری از API هم‌مبدأ می‌رود و [Service Worker فعلی](../apps/web/public/sw.js) آن را cache نمی‌کند.

پس از پیاده‌سازی، در `apps/web` با وابستگی‌های lockfile، `npm test`، `npm run typecheck`، `npm run lint` و `npm run build` را اجرا کنید. برای تست مرورگر با وب در حال اجرا، مثلاً `WEB_TEST_ORIGIN=http://127.0.0.1:3000 npm run test:browser` را بزنید؛ خود تست درخواست‌های API را بدل می‌گیرد. از ریشه نیز `PYTHONPATH=apps/api .venv/bin/python -m unittest discover -s apps/api/tests -p test_activity_assistant.py -v` برای قرارداد بک‌اند موجود قابل اجراست. نتیجهٔ واقعی هر مرحله را جدا ثبت کنید؛ تست mock جای smoke با provider واقعی نیست.

## اجرای بک‌اند برای تست

اجرای عادی از [README](../README.md) و [سند MongoDB](24-mongodb-storage.md) پیروی می‌کند: `DATA_BACKEND=mongo` و endpoint عمومی، حتی در localhost. `LLM_PROVIDER=demo` پیش‌فرض و بی‌نیاز از کلید مدل است؛ در CI از درخواست پولی استفاده نشود. برای smoke واقعی در محیط مجاز، فقط روی سرور `LLM_PROVIDER=gapgpt` و `GAPGPT_API_KEY` را تنظیم و API را دوباره راه‌اندازی کنید. `GAPGPT_ASSISTANT_MODEL=gpt-4.1-mini` و `GAPGPT_IMAGE_MODEL=gemini-2.5-flash-image` پیش‌فرض‌های ثبت‌شده در config هستند. تنظیمات مدل و secret جایی در فرانت یا `NEXT_PUBLIC_*` ندارند.

برای smoke، با نشست یک حساب آزمون و یک revision منتشرشده، وضعیت، تولید راهنما، تولید تصویر و GET باینری، سپس یک سؤال چت را از مرورگر بررسی کنید. اگر provider به‌جای base64، URL تصویر روی CDN دیگری بدهد، فقط میزبان دقیق تأییدشده را در `GAPGPT_IMAGE_HOSTS` سمت سرور اضافه کنید. سرور برای شروع تولید، سقف روزانهٔ حساب/کل برنامه دارد: تصویر ۲۰/۱۵۰ و راهنما ۳۰/۳۰۰. چت واقعی ۱۰ درخواست در دقیقه و ۶۰ در روز برای هر حساب و ۱۲۰۰ در روز برای کل برنامه دارد. دارایی موفق تا ۳۰ روز و مکث معمول شکست ۲ دقیقه است؛ پس از توقف API، رزرو تولید ممکن است تا ۳ دقیقه pending بماند. این اعداد برای فهم رفتارند؛ فرانت از وضعیت و مهلت اعلام‌شدهٔ API پیروی کند.

وضعیت این تحویل: فقط راهنمای پیاده‌سازی است. رابط، مرورگر، MongoDB و GapGPT برای این تغییر مستند اجرا نشده‌اند.
